### 阶段一·A：三栏骨架 + 菜单栏/状态栏 + 布局系统 + 窗口自适应（当前阶段）

> 在阶段一骨架基础上，搭建设计器主界面为**菜单栏 + 三栏面板 + 状态栏**整体布局，引入 UICS 布局引擎与窗口 resize 同步，使整体随窗体大小自适应。此阶段落地了 `layouts/main_layout.json` 与 `src/App.cpp` 的窗口同步逻辑，为后续画布/工具箱/属性面板提供响应式容器。

- **整体布局（v-flow + h-flow 嵌套）**：root panel 采用 `layout: {"type":"v-flow","gap":0}`，纵向三段：
  ```
  root (v-flow)
  ├── menuBar      (menu-bar, 固定高 barHeight:28)
  ├── middleArea   (panel, flowWeight:1 弹性, 内含 h-flow 五元素链式布局)
  │   ├── toolboxPanel   (flowWeight:0, 固定宽 240; layout: anchor, 内含 TabControl)
  │   │   └── toolboxTabs   (tab-control, anchor: fill, 三 Tab: 工具箱/控件树/资源)
  │   ├── splitter1      (splitter, orientation:"vertical", 厚 6)
  │   ├── canvasArea     (flowWeight:1, 弹性填充)
  │   ├── splitter2      (splitter, orientation:"vertical", 厚 6)
  │   └── propertyPanel  (flowWeight:0, 固定宽 240)
  └── statusBar    (status-bar, 固定高 28)
  ```
- **toolboxPanel 内部 TabControl**（v1.1.1 原生控件）：`toolboxPanel` 设 `layout:{"type":"anchor"}`（内部 anchor 布局），子 `toolboxTabs`（`type:"tab-control"`）用 `anchor:"fill"` 铺满父容器；三 Tab **各含一个 `tree-view` 页**（均 `anchor:"fill"` 铺满 tab 页内容区）：
  - **工具箱**（`tvToolbox`）：类型注册表控件分组树（基础/容器/高级控件分组节点 + 控件叶子，后续动态填充）
  - **控件树**（`tvTree`）：画布控件层级树（后续由 `TreeView` 命令式填充内存模型）
  - **资源**（`lvResource`）：resourceProviders 列表（**list-view** 两列：名称/路径，columns+rows —— 资源为平面 name/path 映射，非层级树）
  `anchor:fill` 使 TabControl/TreeView 随 toolboxPanel 高度自动跟随（窗口 resize 时 middleArea→toolboxPanel→TabControl→TreeView 高度链式更新）。TabControl/TreeView JSON 均需保留 rect（LayoutParser 要求），anchor 提供 fill 语义。
- **Splitter 引擎模式（v1.1.1 增强，`docs/controls/splitter.html` §4.21.7）**：Splitter 放布局引擎容器（panel + h-flow/v-flow）children 中即自动进入**引擎模式**——成为引擎一等元素，**无需 firstPanel/secondPanel 关联**，两侧面板就是它的前后邻居，任意数量 Splitter 按链式累计布局（三栏/四栏/嵌套均支持）：
  - JSON：`{"type":"splitter","id":"splitter1","orientation":"vertical","thickness":6,"ratio":0.2,"minFirst":100,"minSecond":100}`；**Splitter 节点必须排在关联面板之后**；`orientation:"vertical"` → 左右分栏（竖条），其余为水平；rect 可省略（由前后面板边界自动推导）
  - 分段语义：Splitter 占自身 thickness 宽，与邻居之间不计 gap；流内固定/弹性分配不变（flowWeight 生效）
  - 拖拽：引擎整链重排（前段固定→改前段固定宽；前段弹性且后段固定→改后段固定宽；双侧弹性→前段锁定为固定），多个/嵌套 Splitter 位置始终链式正确、互不覆盖
  - 事件：`onSplitterMoved`（binding 事件名 `moved`，`GetMovedPosition()`）在拖拽结束（endDrag）及 setSplitRatio 后触发
  - **实测结论**（2026-08-29）：引擎模式拖拽体验正常；窗口 resize 时**引擎整链自动重排**——splitter1 保持（左栏固定 240）、canvas 弹性填充、splitter2 与 property 随 canvas 自动链式移动（实测 1600×1000：toolbox 240 / splitter1 240 / canvas 1108 / splitter2 1354 / property 1360），**无需应用侧手动同步 splitter 位置**
  - **实现沿革**：早期 v1.1.1 版本 LayoutParser 解析 splitter JSON 节点会阻塞、多 splitter 共享中间面板（first/second-linked 自动模式）区域冲突 → 曾用命令式 workaround（`CreateSplitter` + 手动 `syncSplitterLayout`）；v1.1.1 更新后 **JSON 引擎模式可用，workaround 已移除**
- **菜单栏/状态栏原生控件**：`menu-bar`（menus 数组，含 caption/shortcut/separator/子菜单/events.onClick）与 `status-bar`（items 数组，含 id/text/align）。两者为**全宽/独立控件**，挂入 v-flow 容器时自动切换手动定位参与布局引擎重排（v1.1.1 增强，见 `docs/controls/menu.html` §4.14.7），无需显式 `manual-position`。
- **窗口可调整大小**：`Config.WithWindowFlags(UIWindowFlags::Resizable)`（binding 头 `UICornerstone.h` 语义化窗口标志，值对齐 SDL3 `SDL_WINDOW_RESIZABLE`，勿用硬编码数值）。
- **窗口 resize 同步 root**（`src/App.cpp` `syncRootToWindow()`）：
  - UICS binding **未暴露窗口尺寸查询**，故动态解析 `SDL3.dll` 的 `SDL_GetWindowSize / SDL_SetWindowSize / SDL_GetWindows`（`App::SdlApi`）
  - 主循环每帧调用 `syncRootToWindow()`：取当前窗口尺寸，若与上次不同则 `root.SetRect(0,0,w,h)` → 触发 v-flow 整体 reflow（menuBar 顶、middleArea 弹性、statusBar 底）+ middleArea 内 h-flow 五元素 reflow（面板按 flowWeight 重排、splitter 占 thickness）
  - 引擎 resize 时自动整链重排（splitter1 保持、splitter2/property 随 canvas 弹性链式移动），应用侧无需手动同步 splitter
  - `App.h` 增加 `SdlApi`（SDL 窗口 API 动态解析 + `windowHandle()`）与 `m_lastWinW/m_lastWinH` 缓存
- **布局引擎选型结论**（验证记录）：三栏中间自适应**不能用 anchor 的 `fill`**——`fill` 是铺满整个父容器（会盖住左右面板）；正确方案是 **h-flow + flowWeight**（中栏 `flowWeight:1` 弹性）。锚点布局的 `LEFT_STRETCH/RIGHT_STRETCH` 虽能固定左右宽度并拉伸高度，但中间无"填充两兄弟之间剩余"的锚值。
- **锚点值大小写**：文档写 `LEFT_STRETCH`（大写），但实际 JSON 布局解析用小写 kebab `left-stretch`（PropertyNames `kJsonAnchorLeftStretch` 一致）。实现时以 **kebab 小写**为准。
- **v1.1.1 更新验证记录**（2026-08-28，UICornerstone 主设计开发修复后）：
  - 早期版本 v-flow 存在缺陷：menu-bar `barHeight:28` 未生效（实际 32）、middleArea `flowWeight:1` 不弹性填充、status-bar 高度异常 56
  - 主设计开发更新 v1.1.1 后重新验证**全部正常**：menuBar (0,0) 宽随窗口高 28；middleArea 弹性填充（如窗口 1600×1000 → 高 944 = 1000−28−28）；statusBar 底部高 28；canvasArea 中栏弹性（1120×944）
  - 结论：**menu-bar/status-bar 挂入 v-flow + flowWeight 弹性是正确方案**，无需绝对定位手动同步
- **单布局文件**：`CMakeLists.txt` POST_BUILD 仅保留 `copy_if_different layouts/main_layout.json → <exe>/main_layout.json` 单份拷贝（`copy_directory layouts` 会产生冗余的 `<exe>/layouts/main_layout.json`，已移除）。
- 验收：`auto=<秒>` 干净退出；运行中拖拽窗口边缘，菜单栏（顶）、三栏（左/右固定 + 中弹性，中间两分隔条可拖拽调整栏宽）、状态栏（底）整体随窗口自适应；手动拖拽两个 Splitter 分隔条体验正常（引擎整链重排三栏宽度）。

### 阶段一·E：画布子视口 + 纸面网格（当前阶段）

> 在阶段一·D 基础上实施画布核心：canvasArea 内容区创建**子视口**（承载被设计布局内容，
> 依赖 UICornerstone v1.1.1+ 视口事件回退），纸面+网格按最初设计画在**子视口内部**，
> 网格接入引擎新能力 **scale-type=tile**（BindingCanvasGrid_Design）。

- **子视口**：`CanvasPane::refreshLayout()` 经 `CreateViewport(areaX, areaY+40, contentW, contentH)`
  创建/同步（窗口绝对坐标）；App 主循环显式驱动 `ProcessEvents/Update/Render`（事件回退要求）。
- **网格瓦片化**：小瓦片纹理（白底 + #303030 1px 线，4×4 格/瓦片）经 `RegisterResource` +
  视口内 `CreateImage("provider:dc_canvas_grid", 0,0,contentW,contentH)` + `scale-type=tile` 平铺铺满：
  - **resize/splitter 零纹理重建**：仅 `SetViewport` + 网格 `SetRect`；
  - **-/+ 缩放**：重建小瓦片（240×240 @1.5x，Debug 实测 ~19ms，低频可接受）；
  - 每瓦片 4×4 格，降低每帧平铺绘制调用数（@160px 瓦片 ≈ 25 次）。
- **资源顺序关键**：绑定层内存 provider 在**首次 RegisterResource 时才创建并挂载 owner**，
  子视口初始化时仅拷贝 owner 的 provider 指针——**瓦片注册必须先于视口创建**（`CanvasPane::Create` 顺序）。

## P0-104 案例复盘：打开工程后"文件"菜单面板闪动（2026-10-18 ~ 10-20）

### 一、现象与触发矩阵

- **现象**：打开含"菜单栏"控件的工程后，设计器窗口顶部"文件"菜单面板区域**闪动约 1–2 秒** ✗；无菜单栏控件的工程不闪 ✓。
- **用户对照实验（触发矩阵 ✗，收敛利器 ✓）**：

| 流程 | 开过菜单 | 真实对话框 | 画布重建 | 闪 |
|---|---|---|---|---|
| 打开项目 | ✓ | ✓ | ✓ | **闪 ✗** |
| 新建（菜单项） | ✓ | ✗ | ✗ | 不闪 ✓ |
| 另存为（菜单项） | ✓ | ✓ | ✗ | 不闪 ✓ |
| 命令行打开 | ✗ | ✗ | ✓ | 不闪 ✓ |

### 二、调查过程（假设与排除 ✗）

1. **菜单重开？** → 设计器 `active-index` 时间线全程干净（`-1→0→-1` 后未重开 ✓）→ 排除 ✗；
2. **hover/陈旧鼠标残留？** → 逐帧日志 `hovered=-1 active=-1` 全程 ✗ → 排除 ✗；
3. **RemoveMenu/析构残留（R1/R2 ✗）？** → 引擎确认为**真实缺陷**（开启态移除不完整 / 析构清理依赖 activeIndex ✗）→ 实施修复 ✓（保留为防御性加固 ✓）→ **设计器复测仍闪** ✗（其流程走完整 detach 路径 ✓）→ 非根因 ✗；
4. **Animation 触发？** → 用户最小工程 `Temp/AA.csd`（**仅一个 animation** ✗、无菜单栏 ✗）亦复现 ✗ → 曾疑 animation 加载与菜单面板共享/内存问题 ✗——实为**诊断噪声**：animation 的逐帧变化使区域哈希持续出现差异 ✗（变化集中在动画区 ✓）；
5. **采集时序伪影（引擎指正 ✗）？** → 设计器诊断 `CaptureBench` 位于 `ProcessEvents` 后、`Render/Present` **之前** ✗（读上一帧缓冲 ✗）→ "面板像素 vs 当前状态=-1"= **上一帧**（点击菜单项时菜单仍合法开启的画面 ✗）；
6. **正确时序重测**（采集移至 `Render+RenderOverlays` 后、`Present` 前 ✗）→ **渲染目标无任何面板帧** ✓ → "可见但无 active-index"确为**时序伪影** ✓（引擎判定成立 ✓）——**但用户视觉仍闪** ✗。

### 三、真实根因（视觉层 ✗）

- **模态对话框关闭瞬间，DWM 露出"末次呈现帧"** ✗——即点击菜单项（如"打开项目"）时**菜单仍开启的旧画面** ✗（该帧在模态期间未被替换 ✗）；

### 五、经验教训

1. **采集时序必须与被测对象一致** ✗——读渲染目标须在 **Render 后、Present 前** ✓（否则读上一帧 ✗，产生"幽灵状态分歧" ✗）；
