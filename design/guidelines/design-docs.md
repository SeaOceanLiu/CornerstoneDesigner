# 设计文档规范

## 先想清楚再动手

- 遇到不确定的内容主动询问，不要主观猜测。
- 同一内容存在多种解读方向时，逐条罗列说明。
- 发现更简单高效的处理方式，主动提出建议。
- 遇到逻辑矛盾、信息缺失时及时停止，不强行处理。

## 能简单就别复杂

- 采用最简方式完成任务，不刻意增加复杂度。
- 不为"后续可能使用"额外叠加多余功能与流程。
- 内容、流程明显啰嗦冗余时，及时精简优化。

## 只改该改的内容

- 仅处理和当前任务直接相关的部分。
- 不擅自改动周边无关内容、原有格式与备注。
- 发现其他问题可以文字提醒，不要直接修改。

## 定好目标再执行

- 提前明确任务完成标准，界定"做完"的范围。
- 把单纯"执行动作"，升级为"完成动作 + 结果验证"。
- 复杂多步骤任务，先梳理步骤清单，并说明每一步的验收标准。

## 架构决策原则

- 优先参考项目现有实现的架构，新模块的设计应与已有模块保持一致的接口风格和实现惯例。
- 在确定架构方案前，应详细分析和对比多个方案的优缺点，包括继承层次、事件路由、数据同步、缩放处理等关键维度。
- 分析结论应写入设计文档的"架构选择"或"关键设计决策"章节，说明选型理由和排除方案的原因。
- 依赖 UICornerstone 时，优先复用其现有能力（C++ Binding 封装、视口缩放、RegisterAction 等），不重复造轮子。

## 视觉图规范

- 文档中的图片、视觉效果、流程图、时序图、状态图等，**尽量使用非 ASCII 图**，优先使用矢量图。
- 推荐格式：**SVG**（内联嵌入，可在 draw.io 编辑）、**Mermaid**（流程图/时序图/状态图）、draw.io 导出图。
- 避免使用纯 ASCII 字符画表现视觉布局或逻辑流程。
- 简单示意可在 VS Code / Markdown 预览中先用 Mermaid 快速绘制，复杂图建议用 draw.io 编辑后导出 SVG 内联嵌入。
